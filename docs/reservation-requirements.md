## 1. 何をつくるか

公式LINEから、お客様が **店舗・来店日時・人数** を指定して席の予約を申し込めるようにします。
申し込みは自動では確定せず、**店舗側が内容を見て承認して初めて確定**します（承認制）。

予約は管理画面の「予約台帳」に一覧で貯まり、対応漏れが分かる状態にします。

### やること

- LINEのメニューから予約フォームを開いて申し込める
- 申し込みが予約台帳に入る
- 店舗側が承認 / 却下する
- 電話・DMで受けた予約も、同じ台帳に手入力できる
- キャンセル・来店・無断キャンセルを記録する

### 今回やらないこと

| やらないこと | 理由 |
|---|---|
| キャストの指名予約 | 出勤スケジュールをアプリで管理していないため。指名を受けるには出勤表の入力運用が別途必要 |
| 空席の自動判定 | 電話・当日来店を含めた全予約が台帳に入る運用が定着してから。今やると「確定後に満席でした」の事故が起きる |
| 予約の自動確定 | 上と同じ理由。まずは人が見て承認する |
| 予約時の年齢確認 | 従来どおり**来店時に現地で確認**する |
| お客様のマイページからの予約変更 | まずは電話・LINEでの連絡で対応する |

## 2. 予約の流れ

### お客様側

```
公式LINEのメニュー「予約する」
   ↓
予約フォーム（店舗・日付・時間・人数・お名前・電話番号）
   ↓
「申し込みを受け付けました。店舗からの確認をお待ちください」と表示
   ↓
店舗から確定 or 満席の連絡を受け取る
```

**お申し込みの時点では予約は確定していません。** この点はフォームと完了画面にはっきり書きます。

### 店舗側

```
予約台帳に「未対応」として表示される
   ↓
内容を確認して「承認」または「却下」
   ↓
お客様へ結果を連絡する
   ↓
来店当日、「来店済み」または「無断キャンセル」を記録する
```

## 3. 予約の状態

予約は削除せず、状態を変えて残します（いつ誰がキャンセルしたか後から分かるようにするため）。

| 状態 | 意味 | 誰が変えるか |
|---|---|---|
| 未対応 | 申し込みが届いた直後 | — |
| 確定 | 店舗が承認した | 店舗 |
| お断り | 満席・営業時間外などで受けられない | 店舗 |
| キャンセル | 確定後にお客様都合で取りやめ | 店舗（連絡を受けて記録） |
| 来店済み | 当日いらっしゃった | 店舗 |
| 無断キャンセル | 確定していたが来店がなかった | 店舗 |

## 4. 画面

### 4-1. 予約フォーム（お客様）

| 項目 | 必須 | 内容・制約 |
|---|---|---|
| 店舗 | 必須 | 池袋店 / 日本橋店 / 名古屋栄店 から選択 |
| 来店日 | 必須 | 当日から60日先まで |
| 来店時間 | 必須 | 18:00〜22:00 を1時間刻みで選択（5枠。22:00が最終受付） |
| 人数 | 必須 | 1〜6名 |
| お名前 | 必須 | フルネーム |
| 電話番号 | 必須 | 当日の連絡・本人確認用 |
| 遠隔ドリンクの購入ID | 任意 | BASEの注文ID（16進16桁）。承認の優先に使う。**システムは照合しない** |

- **遠隔ドリンクを買った人を承認で優先します**（2026-09-10 決定）。
  お客様に BASE の注文IDを任意で申告してもらい、台帳の行に「遠隔購入の申告あり」と出す。
  **購入は予約の条件ではない**ので、欄のすぐ下に「※購入しなくても予約申請はできます」と明記する
- ⚠️ **購入IDはシステムでは照合できません。** concafe-app は BASE の API を持っていないため、
  他人の注文IDを書くこともできます。台帳では「購入ID（未照合）」と表示し、
  **承認を優先する前に、店舗が BASE の管理画面で必ず突き合わせる**運用にします。
  形が16桁と違うときは台帳に警告を出しますが、申し込み自体は弾きません
  （BASE以外の経路や表記ゆれで申し込めなくなるほうが損なため）
- **お客様向けフォームに自由記入欄は置きません**（2026-09-10 決定）。
  席の希望・記念日・ご要望は受け付けず、必要なら公式LINEのトークで伺う。
  入力項目が増えるほど離脱するのと、承認前に約束したと受け取られる余地を作らないため。
  `Reservation.note` 列は残し、電話・DMで受けた分を管理画面から手入力するときのメモに使う
- **会員登録は不要**とします（登録必須にすると申し込みのハードルが上がるため）
- 同じ電話番号からの短時間の連続申し込みには上限を設けます（いたずら対策）

### 4-2. 予約台帳（管理画面）

閲覧・操作できるのは**管理者（ADMIN）のみ**です。氏名と電話番号を含むため、一般ページからは一切見えないようにします。

- 一覧: 来店日時順。店舗で絞り込み。「未対応」を最上部に強調表示
- 各予約の詳細と、状態を変える操作（承認 / 却下 / キャンセル / 来店済み / 無断キャンセル）
- 誰がいつ状態を変えたかを記録
- **電話・DMで受けた予約を手入力する画面**（受付経路を LINE / 電話 / その他 で記録）

予約台帳は他の管理項目と混ざらない専用ページにします（誤操作を防ぐため）。

## 5. お客様への連絡方法（要決定）

承認・却下の結果をどう伝えるかは、3つの案があります。

| 案 | 内容 | 手間 | 開発 |
|---|---|---|---|
| **A（推奨）** | 店舗スタッフが公式LINEのトークで手動返信 | 1件ずつ返信 | ほぼ不要 |
| B | 承認するとLINEで自動メッセージが届く | 自動 | LINE連携の開発が必要。送信通数に応じた費用が発生 |
| C | 予約時にメールアドレスももらい、メールで自動通知 | 自動 | 既存のメール送信を流用。ただしメールは見落とされやすい |

まずは **A** を推奨します。現在すでにLINEで対応されている流れをそのまま活かせ、台帳ができることで「返信し忘れ」が可視化されます。件数が増えてから B に進むのが安全です。

## 6. 運用ルール

**11項目とも確定**（#6〜#11 は 2026-09-08、#1〜#5 は 2026-09-09）。
値はすべて `lib/reservation.ts` の `SETTINGS` 1箇所にある。

| # | 決めること | 決めたこと | 状態 |
|---|---|---|---|
| 1 | 予約を受け付ける時間帯 | **18:00〜22:00・1時間刻み**（全店共通）。**22:00が最終受付**で、選べるのは18/19/20/21/22時の5枠 | 確定 |
| 2 | 何日先まで予約を受けるか | **60日先まで** | 確定 |
| 3 | 当日予約を受けるか | 受ける。**来店の30分前まで**。それ以降は公式LINEのトークで直接受ける | 確定 |
| 4 | 1組の最大人数 | 6名まで | 確定 |
| 5 | 承認の目安時間 | 受付から3時間。**0:00〜12:00 は返信できないので数えない** | 確定 |
| 6 | 承認を担当するのは誰か | **店長のみ**（管理画面にアクセスできる人） | 確定 |
| 7 | キャンセルの期限 | **期限なし。いつでもキャンセルできる** | 確定 |
| 8 | 無断キャンセルへの対応 | **記録するだけ。**次回以降の予約は制限しない | 確定 |
| 9 | 定休日・臨時休業の扱い | **システムでは考慮しない。**営業時間外の申し込みは店舗が「お断り」で返す | 確定 |
| 10 | 電話・DM予約の手入力を誰がやるか | **予約は一律で公式HPのフォームに寄せる。**電話・DMで受けた分も、お客様にフォームからお申し込みいただく | 確定 |
| 11 | 店舗ごとに運用が違うか | **違わない。**全店同じ運用 | 確定 |

### #10 について（この決定の意味）

**台帳がひとりでに完全になる。** 全予約が同じ入口を通るので、
「電話で受けた分が台帳に入っていない」という穴が構造的に生まれない。
要件書の初版で「ここが回らないと第3段階に進めません」と書いた懸念は、この決定で解消する。

ただし**当日の電話は現場で必ず発生する**（「今から2人いけますか」）。
そのときお客様にフォームを開いてもらう余裕がないことがあるので、
**管理画面の手入力は例外用として残してある**。使わなければそれで構わない。
手入力は当日の締切（来店2時間前）と過去日の制限を受けないので、後から台帳に足せる。

## 8. 技術メモ（開発者向け・店舗管理者の方は読み飛ばして構いません）

- 既存の concafe-app（Next.js / Prisma / SQLite）に追加。サーバーの増設は不要
- LINE側はリッチメニューから自社サイトの予約ページ `/reserve` を開くだけ（第1段階ではLINEの開発要素なし）
- 予約テーブルの想定項目
  - 店舗ID / 来店日時 / 人数 / 氏名 / 電話番号 / 遠隔ドリンクの購入ID / メモ（管理画面の手入力のみ）
  - 状態（未対応・確定・お断り・キャンセル・来店済み・無断キャンセル）
  - 受付経路（LINE / 電話 / その他）
  - 作成日時 / 更新日時 / 最終操作者
- 状態変更は履歴を残す。レコードは物理削除しない
- 予約データは管理者ロールのみ参照可能。公開側APIとは経路を分離する
- 同一電話番号・同一IPからの連続申し込みに上限を設ける
