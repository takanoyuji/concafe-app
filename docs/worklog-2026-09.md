## 1. 発端 —「ファイルを2つ選べない」（コード変更なし）

店長が「データ2個いれれるかな？と思ったんですがでない」「2つ選択しようとしてるんですが選択できない」と連絡。

### 調べたこと

`app/admin/page.tsx` の売上CSVと人件費CSVは**別々の `<input type="file">`** で、
どちらも `multiple` が無い。1つのダイアログで2ファイルは選べない。

「2ファイルに分かれているのでは」を疑い、エアシフトの書き出し実績を数えた。
`概算人件費シミュレーション_*.csv` の期間を全部並べたところ、
**後半（16日〜末）を1ファイルで書き出した実績が11件**あった。

```
20240816-20240831   20240916-20240930   20241016-20241031
20250216-20250228   20250516-20250531   20260616-20260630 ...
```

エアレジもエアシフトも8/16〜8/31を1ファイルで落とせる。**分割は不要だった。**

### 結論

コードの問題ではなく操作の問題。`multiple` は実装しない。
上のボタンに売上CSV、下に人件費CSVを1つずつ入れれば動く。

### 同時に見つかった2つ（この時点では見送り）

- **期間の初期値が「今日が含まれる期間」**（`page.tsx:89-91`）。9/1に開くと 2026/09 前半になる
- **期間セレクタとCSVの実期間の不一致を検証していない。** `year/month/half` は remodri の
  取得期間にだけ使われ、CSVは中身を全部合計する。8月まるごとのCSVで「後半」を選ぶと
  エアレジ分は月全体・遠隔分は後半だけ、という混ざった数字が黙って出る

どちらも「API化で消えるので後回し」と判断した（→ 8章に後日談）。

## 2. Airレジ API の仕様で効いた点

| | 内容 |
|---|---|
| **遡り62日** | `businessDate` も `updDateTimeFrom/To` も上限62日。1リクエスト最大1日 |
| 固定IP制限 | 申請時に登録したIPからのみ。**開発機（WSL）からは叩けない** |
| キーは店舗単位 | 池袋 / 日本橋 / 名古屋栄で3組。「データ連携API設定」画面で発行 |
| ページング | `nextCursor` |

**62日が設計を決めた。** 取り損ねた日は明細レベルで二度と取れない。
商品別売上CSVは後日でも落とせるが、あれは集計済みで取引明細・支払方法・原価を持たない。

→ **集計方法やDB設計が固まるのを待たず、まず生JSONを確保する**方針にした。
放置すると毎日1日ぶんずつ失われる。

### 発行手順（仕様書の「動作確認」編からFAQ経由で判明）

バックオフィス → 設定 → 他システム連携［データ連携API］→ データ連携API
→ 「API利用」をオン → 規約同意 → APIキー（13桁）をコピー → 「+APIトークンを発行する」

- **店舗ごとに必要**（FAQに「データ連携するすべての店舗でAPI利用設定が必要」）
- トークンは発行時に控える（FAQ「削除した場合、操作のやり直しはできません」）
- 「API利用をオン」を飛ばすとキーが正しくても401（コード2003）

## 3. 生JSONの確保（`ebcbaf8`）

`scripts/airregi-fetch.sh`。bash + curl + jq でホスト側から叩く。

- `includeOrders=1` **かつ `includePaymentMethods=1`**
- 保存先 `airregi-raw/<store>/<businessDate>.json.gz`
- ページング / 429の`Retry-After`準拠リトライ / 401で店舗中断 / `--skip-existing` / `--dry-run`
- 62日超の日付は投げずにスキップ / 一時ファイルに書いてから `mv`

`includePaymentMethods` は給与計算に不要だが、**Airペイの実効料率を明細で定点観測できる**
ようにするため付けた。後から遡って足せない。

### 落とし穴2つ

**`set -e` はシェル全体の設定。** 関数の中で `set +e` → `set -e` と戻すと呼び出し元の `+e` まで
解除され、関数が失敗コードで返った瞬間にスクリプトごと終了する。集計行も中断メッセージも
出ないまま exit 2 になっていた。`|| rc=$?` で受ける形に直した。

**開発機の jq が snap 版で `/tmp` を開けない**（`Could not open file`）。
本番の `/usr/bin/jq` は実体なので問題ないが、開発機で再現しなくなる。jq へは stdin で渡す。

固定IP制限で本物は叩けないため、モックサーバーに対して全経路を確認してから本番へ出した。

## 7. Phase 2: 明細→給与計算の入力（`807e0f7`）

```
parseSalesCsv(buf)            エアレジCSV      ─┐
buildSalesRows(...)           取り込み済み明細  ├→ SalesRow[] → calculateSalaryFromRows()
calculateSalary(csvBuf, ...)  従来の入口。上2つを呼ぶだけで挙動は不変
```

**畳む粒度は CSV と同じ「商品×バリエーション×カテゴリー×税区分」。**
業績サマリの外税→税込換算が `Math.round()` を行ごとに掛けるので、
カテゴリー単位まで畳むと丸めの位置が変わって数円ずれる。

**期間に取り込み漏れがあれば計算させない**（`assertPeriodComplete`）。
欠けたまま計算すると、その日の売上が丸ごと抜けた給与がそれらしく出る。
取引0件の日は台帳に `ok` で載るので欠けにならない。

### 集計式（確定）

```
販売総売上 = discountedPrice × orderCount + (discountTotal // 0)
粗利総額   = 販売総売上 − cost × orderCount
             taxType == "0"（内税）なら さらに − 販売総売上 × 0.1
カテゴリー = categoryName（"遠隔_" 接頭辞をそのまま含む）
返品       = transactionType == "1" を全項目で減算
```

**Phase 3（並行稼働の突合UI）は実装しなかった。** 8月までの実データで突合が済み、
売上・粗利とも残差0円を確認できたため（高野判断）。

## 8. Phase 4: CSVを既定から外す／割引後へ切替（`04a1c31`）

給与APIの `source` の既定を `api` にした。売上CSVの欄は残す
（取り込みが止まっているとき、62日より前を計算し直すとき用）。

`source=api` のときは `salesCsv` が来ていても見ない。黙って無視されるのを避けるため、
管理画面は API に切り替えた時点で選択済みのファイルを外す。

### 業績サマリを割引後にした

```
売上（税込） += orderDiscount        割引額そのまま
売上総利益   += orderDiscount × 0.9  内税の行と同じ扱い
```

最初は「売上と粗利を同額引けば仕入が動かない」と実装したが、
消費税が `÷11` で計算されるぶんズレて**テストで仕入が45円動いた**。
全体割引は税込（仕様書「全体割引適用金額(内税込み)」）なので、
内税の行が `粗利 -= 売上 × 0.1` と処理されているのに合わせる形に直した。

⚠️ **キャストのバックからは引かない。** 全体割引は伝票単位でどのキャストの売上か決められない。
結果としてキャスト別粗利の合計と店舗の粗利は、この金額のぶん一致しない（月あたり数百円規模）。

### 既定変更で既存テストが5件落ちた

`source` を送らない経路が API に落ちたため。**既定変更の影響が正しく出た形**なので、
売上CSV経路を試す2ファイルに `source=csv` を明示した。

### 1章で見送った「期間の初期値」が効いてくる（未対応）

これまでは売上CSVを選ぶと `detectPeriodFromFilename` が期間を自動で合わせていた。
**API既定になって売上CSVを選ばなくなったので、この自動補正が発動しない。**

ただし `assertPeriodComplete` が未来の営業日を「未取得」として弾くため、
**壊れた数字は出ず、失敗する側に倒れる。** エラーメッセージが
「取り込めていない営業日が14日あります」となって分かりにくいだけ。
2026-09-02 時点では直さない判断。

## 10. バックアップの穴

調べたところ **concafe のDBは7日分が同じディスクにあるだけで、サーバー外にコピーが1つも無かった。**
キャスト・ポイント履歴・給与履歴が入っており、生JSONより先に塞ぐべき穴だった。

- `backup-db.sh` が Airレジの生JSONも tar して保存するようにした
- 保持を7日 → **30日**に延長（DB 3.7MB + 生JSON 0.6MB なので容量は誤差）
- サーバー外への退避手順を `docs/OPERATIONS.md` に追記。**`--delete` は付けない**
  （サーバー側で消えても手元に残すため）。WSLは常時起動でないので自動化はしない

生JSONは Phase 1 のデプロイで「原本」から「二次アーカイブ」に降格した。
パース済みデータがDBに入りバックアップ対象になったため。
それでも API が62日より前を遡れないので、消すと取り直せないことは変わらない。
