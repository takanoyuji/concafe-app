# Airレジ API 連携

給与計算・業績集計の入力を、エアレジ売上CSVの手アップロードから API 取得へ移す作業の記録。

## なぜ「まず生JSONを取る」から始めるか

**Airレジ API は `businessDate` を 62日 までしか遡れない**（IF定義書_01 取引情報取得 p.1）。
取り損ねた日は、あとから**明細レベルでは二度と取得できない**。
商品別売上CSVは後日でも落とせるが、あれは集計済みで、取引明細・支払方法・原価を持たない。

したがって集計方法やDB設計が固まるのを待たず、**先に生JSONを確保する**。集計は保存したJSONから何度でもやり直せる。放置すると毎日1日ぶんずつ失われる。

## 決まっていること

| | 決定 |
|---|---|
| 取得する情報 | 取引情報取得API。`includeOrders=1` **かつ `includePaymentMethods=1`** |
| 保存形式 | レスポンスJSONを**そのまま**保存。正規化列だけ持つことはしない |
| 日次の遡り窓 | **45日**（直近2半期）。会計金額修正・伝票削除が後日発生するため毎日取り直す |
| 62日より前 | **バックフィルしない。** 過去の業績は `SalaryPeriod` の確定値を正とする |
| 切替の合格ライン | **粗利とキャスト別支払額は1円一致。売上サマリは「差＝全体割引総額」が1円まで成立すること**（下記で検証済み）。満たすまでCSVを既定から外さない |
| 全体割引の扱い | **割引後（APIの `totalAmount`）を正とする**（2026-09-02 高野判断）。現行CSVは割引前なので、移行後は売上サマリが全体割引ぶん小さくなる。それが正しい姿。明細への按分はしない |
| 業務日付変更時間 | 設定値を持たない。集計は `businessDate` で切る。**実データから3店舗とも5時と判明**（下記）。日次cronは 8:00 JST |

`includePaymentMethods=1` を付けているのは給与計算のためではない。**Airペイの実効料率を明細で定点観測できるようにするため**で、後から遡って足せないので最初から取る。

## 制約

- **固定IP制限。** 申請時に登録した `219.94.244.166`（本番サーバー）からしか叩けない。**開発機（WSL）からは動かない**
- **キーとトークンは店舗単位。** 池袋 / 日本橋 / 名古屋栄でそれぞれ必要。Airレジ「データ連携API設定」画面で確認・発行
- 1リクエストの期間は最大1日。`nextCursor` でのページングあり
- レートリミットあり（429 + `Retry-After`）

### ⚠️ 返品の `totalAmount` はプラス値で返る

実物（名古屋・2026-07-22）:

```json
{"transactionType":"1","refundType":"0","originalVoucherNo":"000220260722225249653",
 "checkDate":"20260722","businessDate":"20260722","totalAmount":2450,"taxAmount":222,

            "orderCount":1,"discountedPrice":2450,"cost":450,"taxType":"0"}]}
```

**返品なのに金額が正の値。** 集計時に `transactionType=="1"` を明示的に減算しないと、返品のぶんだけ売上と粗利が二重に膨らむ。

`transactionDateTime` の日付と `businessDate` がズレる取引の時刻分布から逆算した。

| 店舗 | 前日扱いの最終時刻 | 当日扱いの最初の時刻 | 判定 |
|---|---|---|---|
| tokyo | 04時 | 05時 | **5時** |
| osaka | 04時 | 06時 | 5時（05時台に取引が無く厳密には未確定） |
| nagoya | 04時 | 05時 | **5時** |

### 原価0の明細は設定漏れではない（B-3 確定）

東京の原価0明細387件の内訳（上位）:


### Phase 2 の集計式（確定）

```
販売総売上 = discountedPrice × orderCount + (discountTotal // 0)
粗利総額   = 販売総売上 − cost × orderCount
             taxType == "0"（内税）なら さらに − 販売総売上 × 0.1
カテゴリー = categoryName（"遠隔_" 接頭辞をそのまま含む）
税区分     = taxType  0→内税 / 1→外税
返品       = transactionType == "1" を全項目で減算
売上サマリ = totalAmount（全体割引適用後）を採用
```

### 取り込まない条件（黙って通さない）

- **生JSONの `storeNo` が `Store.airRegiStoreNo` と違う** … 別店舗のAPIキーで取れたデータの混入を止める。
  2026-08-16 に名古屋のCSVで東京の給与計算が保存され、東京のキャスト17人が全員0円になった事故があった。
  同じ失敗をデータ層で止めるための照合
- ファイルの中の営業日がファイル名と違う
- ページに `code != "0000"` のエラー応答が混ざっている（0件として取り込ませない）
- `Store.airRegiStoreNo` が空の店舗は「連携対象外」として飛ばす（エラーにはしない）

## Phase 2（明細→給与計算の入力）— 実装済み・未デプロイ

### 構成

```
lib/salary.ts
  parseSalesCsv(buf)            エアレジCSV      ─┐
  buildSalesRows(...)  ←lib/airregiSales.ts      ├→ SalesRow[] → calculateSalaryFromRows()
                        取り込み済みの取引明細   ─┘
  calculateSalary(csvBuf, ...)  従来の入口。中身は上の2つを呼ぶだけで挙動は不変
```

`calculateSalary()` の**シグネチャも挙動も変えていない**。既存の呼び出し元とテストは無改造で通る。

給与APIは `source` で切り替える。**既定は従来どおり `csv`。** `source=api` のときだけ
売上CSVが不要になり、取り込み済みの取引明細から作る（人件費CSVは引き続き必要）。

### 畳む粒度は CSV と同じ「商品×バリエーション×カテゴリー×税区分」

業績サマリの外税→税込換算は `Math.round()` を**行ごとに**掛ける。
カテゴリー単位まで畳むと丸めの位置が変わり、数円ずれることがある。

### 期間に取り込み漏れがあれば計算させない

`assertPeriodComplete()` が、期間内の営業日すべてに `ok` の台帳があるかを確認する。
1日でも欠けていれば 400 で止める。**欠けたまま計算すると、その日の売上が丸ごと抜けた給与が
それらしく出てしまう**ため。取引0件の日は台帳に `ok` で載るので欠けにはならない。

### ⚠️ 全体割引は、まだ割引前のまま

「割引後が正しい」という判断（2026-09-02）に対して、**Phase 2 時点の業績サマリは割引前**になっている。
全体割引は伝票単位で商品明細に按分できないため `SalesRow` に乗らず、結果として現行CSVと同じ基準になるため。

これは意図的に残している。**Phase 3 の突合で差が0になり、名寄せの検証に集中できる**からで、
割引後への切り替えは Phase 4（CSVを既定から外すとき）に行う。
`SalarySummary` に全体割引の総額を持たせて差し引く形になる見込み。金額は月あたり数百円規模。

## Phase 4（売上CSVを既定から外す／割引後へ切替）— 実装済み・未デプロイ

Phase 3（並行稼働の突合UI）は**実装していない**。8月までの実データで突合が済んでおり、
売上・粗利とも残差0円を確認できたため（2026-09-02 高野判断）。

### 売上の出どころは Airレジ API が既定

給与APIの `source` の既定を `api` にした。管理画面にはラジオボタンを置いてある。

| | 既定 | 売上CSV | 人件費CSV |
|---|---|---|---|
| **Airレジ API** | ✅ | 不要 | **必要**（みせ勤 移行まで） |
| 売上CSV | | 必要 | 必要 |

**売上CSVの欄は残してある。** 取り込みが止まっているとき、62日より前の期間を計算し直すときに使う。

⚠️ `source=api` のときは `salesCsv` が来ていても見ない。黙って無視されるのを避けるため、
管理画面は API に切り替えた時点で選択済みのファイルを外す。

### 業績サマリは全体割引の適用後

「割引後が正しい」という判断（2026-09-02）を反映した。

```
売上（税込） += orderDiscount            割引額そのまま（マイナス値）
売上総利益   += orderDiscount × 0.9      内税の行と同じ扱い（割引は税込のため）
貢献利益     = 売上総利益 − キャスト給与  上記の影響を受ける
仕入         = 売上（税抜）− 売上総利益   ほとんど動かない
```

粗利を9割にしているのは、**全体割引が税込**（仕様書「全体割引適用金額(内税込み)」）で、
内税の行が `粗利 -= 売上 × 0.1` と処理されているのに合わせるため。

⚠️ **キャストのバックからは引かない。** 全体割引は伝票単位で、どのキャストの売上かを決められない。
この結果、キャスト別粗利の合計と店舗の粗利は、この金額のぶんだけ一致しない。金額は月あたり数百円規模。

`SalarySummaryRecord.orderDiscount` に総額を残すので、何をいくら引いたかは後から確認できる。
CSV経路では常に0（CSVに全体割引が載っていないため）。

### 落とし穴

- **`set -e` はシェル全体の設定**。関数の中で `set +e` → `set -e` と戻すと呼び出し元の `+e` まで解除され、関数が失敗コードで返った瞬間にスクリプトごと終了する。`|| rc=$?` で受けること（実際にこれで集計行が出ないバグを踏んだ）
- **jq へは stdin で渡す。** snap版 jq はファイル引数のパスを開けない（`Could not open file`）。本番の `/usr/bin/jq` は実体なので問題ないが、開発機で再現しなくなる
