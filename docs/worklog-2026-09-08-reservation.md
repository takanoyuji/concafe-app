## 2. 設計で効かせた判断

**来店日時を DATETIME にせず、`visitDate` / `visitTime` の文字列2列で持つ。**
本番のコンテナはUTCで動く。DateTimeで持つと「19:00で申し込まれたものが10:00で出る」類の
ズレが、表示・集計・CSVのどこか1箇所を直し忘れた瞬間に出る。JSTの文字列で入れて文字列のまま出せば
その事故が起きない。並び替えは `(visitDate, visitTime)` の辞書順でそのまま日時順になる。
現在時刻との比較が必要な箇所（当日締切・受付上限）だけ `jstNow()` でJSTに直して比べる。

**公開APIは `status` と `source` を受け取らない。**
受け取ると、フォームを通さず「確定済み」の予約を外から作れてしまう。
公開APIが作れるのは `PENDING` / `source=LINE` だけに固定した。実データで確認済み（下記）。

**状態遷移をホワイトリストで縛る。**
「来店済み → キャンセル」「確定 → 未対応」のような、後から台帳の意味が変わる操作を弾く。
台帳を後で空席判定の入力に使う前提なので、履歴が信用できないと第3段階に進めない。

**予約は物理削除しない。** 変更は毎回 `ReservationEvent` に積む（誰が・いつ・何から何へ）。
お客様の申し込みも `fromStatus=""` の1件として残る。

**IPそのものは保存しない。** 連続申し込みの判定に使うだけなので、塩付きのハッシュを持つ。

**運用の数字は `lib/reservation.ts` の `SETTINGS` 1箇所に集めた。** 画面・APIの両方がここを見る。

### #5 の「0時〜12時は返信できない」を素直に実装すると壊れる

経過時間をそのまま数えると、**深夜に届いた申し込みは朝には全部 ⚠️ になる**。
店舗が悪いのではなく返信できない時間帯なのに警告が点くので、
⚠️ が「いつも点いているランプ」になり、本当に返し忘れているものが埋もれる。

`replyableMinutes()` を足して、**12:00〜24:00 に入っている分だけを数える**ようにした。
23:00 に届いた申し込みは、24:00 までの1時間を数えたあと翌12:00 まで止まり、翌14:00 に3時間へ到達する。

### #3 の「30分前まで」は、弾いて終わりにしない

「直前は公式LINEに連絡してもらうのでフォームでは不要」という回答なので、
締切に掛かったときのエラーに**行き先を書いた**。

> このフォームでのご予約は来店の30分前までです。お急ぎの場合は公式LINEのトークからご連絡ください

同じ文言をフォームの下にも常時出してある。締切で止めるだけだと、
お客様がどうすればいいか分からず、そのまま離脱する。

### #10 の決定でひとつ懸念が消えた

要件書の初版で「手入力が回らないと台帳が不完全になり、第3段階に進めない」と書いた。
**全予約を同じ入口（公式HPのフォーム）に通すことにしたので、この穴は構造的に生まれない。**

ただし当日の電話は現場で必ず発生する（「今から2人いけますか」）。
その場でフォームを開いてもらえないことがあるので、**管理画面の手入力は例外用として残した**。
ボタンの文言を「電話・DMで受けた予約を入力する」から「例外的に手入力する」に変え、
原則は公式HPである旨を画面に書いてある。手入力は当日の締切と過去日の制限を受けない。

#7〜#9 は「実装しないと決めた」ものなので、コードにコメントで残した
（`lib/reservation.ts` の `ALLOWED_TRANSITIONS` と `SETTINGS.openTime` の上）。
無いのではなく要らないと決めた、が後から読んで分かるようにするため。

## 4. 動作確認

本番ビルドを別ポート（3101）で起動し、検証用の空DBに対して実際にHTTPで叩いて確認した。
`dev.db` と本番DBには触れていない。

- `/reserve` が200で、承認制の注意書き（「ご予約は確定しません」）がHTMLに入っている
- 申し込み → `{"status":"PENDING"}`。DBも `PENDING` / `source=LINE`
- **`status:"CONFIRMED"` を混ぜて送っても `PENDING` で入る**
- 7名の申し込みは400（「6名を超えるご予約はお電話で…」）
- 未ログインで `/api/admin/reservations` → 403、`/admin/reservations` → 307（proxy.ts が弾く）
- 承認 → 確定、確定→未対応 は409、来店済み→キャンセル も409
- 履歴が3行（新規→PENDING / PENDING→CONFIRMED / CONFIRMED→VISITED、操作者のメール付き）
- 電話予約を過去日で手入力できる。一覧は来店日時順
- `createdAt` を4時間前にした未対応が `overdue=true` になる

`npx vitest run` は 134件すべて通る（115 → **134**）。`npm run build` も通る。

2026-09-09 に確定値を入れたあと、同じやり方でもう一度確認した。

- フォームの時刻の選択肢が 18:00〜22:00 の**5つ**（1時間刻み・22:00が最終受付）
- 61日先は400（「ご予約は60日先まで承っています」）、60日先は201
- 1時間刻みに無い 19:30 は400（時間の選択肢はサーバー側でも突き合わせている）
- JST 17:32 に当日18:00枠を申し込むと400で、**公式LINEへの案内が本文に入る**
- 受付から4時間の未対応が `overdue=true`、2時間は `false`

## 6. デプロイ時の注意

デプロイすれば自動で当たる（Dockerfile の CMD）。手で流す必要はない。

ビルドは開発機で行い、イメージを転送する（本番でビルドしない）。手順は `CLAUDE.md` と
`docs/OPERATIONS.md`。ブランチの正は `production`。

`add_order_discount` / 今回の `add_reservation`）。本番の適用状況は別なので、
