# キャストテーブル統合の記録（2026-08-14 適用済み）

HP掲載用の `Cast` と給与計算用の `CastMaster` に同じ人物が分かれて存在していたのを、
`Cast` 1つに統合した。HPに出すかどうかは表示FLG（`isPublished`）で決める。

## 統合前の状態

| | `Cast`（HP用） | `CastMaster`（給与用） |
|---|---|---|
| 件数 | 29件 | 35名 |
| 店舗 | `storeId` で1店舗のみ | 3店舗分のエアレジ名を横に持つ |
| 相互の関連 | **リレーション無し。`hpName` の文字列一致だけ** | 同左 |

名前が一致するのは28名。給与マスタにしかいない7名、HPにしかいない1名がいた。

## 統合の向きを間違えてはいけない

**`Cast` を土台にして `CastMaster` を合流させる。逆向きにはできない。**

`Cast.id` は次から参照されている。振り直すと紐付けが切れる。

- `PointLedger.castId` … 495件（誰が誰にドリンクを贈ったか）
- `User.favoriteCast1Id` / `favoriteCast2Id` … 321件（お気に入り）

移行では既存の `id` をそのまま維持している。

## 統合後の構造

```
Cast（1人1レコード）
  id            ← 既存のまま。絶対に振り直さない
  castCode      ← 不変コード。remodri が参照する
  name
  isPublished   ← 表示FLG。true のキャストだけHPに出る
  retired       ← 退職FLG。給与集計から外れる
  rank / bio / imageUrl / SNS / order
  各店舗のエアレジ名・エアシフト名（給与計算用）
  stores[]      ← CastStore。掛け持ちに対応

CastStore
  castId / storeId
  isPrimary     ← 主たる店舗。HPではこの店舗のページにだけ出る
```

## 決めたこと

### HPに出るのは主たる店舗のページだけ

掛け持ちが8名いるが、HPに出すのはメイン店舗のみ。掲載人数は統合前と同じ
（池袋11 / 日本橋9 / 名古屋栄5）。掛け持ち情報は給与計算では使うが、HPには出さない。

メイン店舗は統合前の `Cast.storeId`（HP上どの店舗のページに出ていたか）を引き継いだ。
掛け持ち先は給与マスタでその店舗のエアレジ名が入っていることから判定している。

**キャストが複数店舗を回るのは常態**（会社として出張を推奨している）。
掛け持ちは異常データではない。

### 退職者はHPに出さない

`PUBLIC_CAST_WHERE` に `retired: false` を追加した。表示FLGを落とし忘れても出ない。

### CSV取込の「CSVに無い人を退職扱い」は既定オフ

統合により `Cast` が唯一のマスタになったため、給与用CSVに載っていないだけの
HP専用キャストを巻き込む危険が出た。退職させるときは明示的に指定する。

### rank は空文字を「未設定」とする

給与計算が空文字前提で書かれているため、nullable にせず `String @default("")` にした。

## 適用時の検証結果

本番のコピーで移行を流してから適用した。

- 統合後36名（両方28 / 給与のみ7 / HPのみ1）
- ポイント履歴495件の参照切れ **0件**
- `castCode` の重複・空 0件、既存35名のコードは維持
- 所属店舗が付かないキャスト 0名、メイン店舗の重複 0件
- 他8テーブルの件数はすべて不変

お気に入りの参照切れが7件あるが、**統合前から同数**（削除済みキャストを指したまま
残っているユーザー）。統合が原因ではないことを適用前後の比較で確認している。
